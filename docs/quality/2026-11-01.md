# Quality check, 2026-11-01

The ten engineering rules, checked against the code on `main`, with the evidence. Run on Windows 11
with Go 1.26.10, Python 3.14 and Node.js 24.

| # | Rule | Status | Evidence |
|---|---|---|---|
| 1 | Assume every call can fail | pass | The gateway's inventory client has a 5 s `http.Client.Timeout` (`server.go`). The server has read-header, read, write and idle timeouts (`cmd/gateway/main.go`). The worker's `fetch` uses `AbortSignal.timeout(5000)`. SQLite opens with a busy timeout in Python and Node. Queue retries are bounded by `maxAttempts` (3), after which the message is dead. Errors are not swallowed: a failed publish is recorded on the PRODUCER span (the OTel context manager records exceptions), its stock is released, and the caller gets 503. The worker records each failure on its span and in `last_error`. The `.catch(() => undefined)` in `runWorker` only ends the abortable sleep on shutdown. Each `catch {}` in `message.ts` turns malformed input into "no headers" or a poison-message error, by design. |
| 2 | Writes safe to retry | fixed | `POST /reservations` was not idempotent: a retried request with the same `order_id` reserved stock and published a message twice. The inventory now remembers accepted orders. A repeat with the same content returns the first `message_id` without side effects; the same `order_id` with other content gets 409; an order whose publish failed can be retried (`test_a_retried_reservation_reserves_and_publishes_once`, `test_concurrent_retries_of_one_order_reserve_once` with 16 parallel retries, `test_a_reused_order_id_with_other_content_is_refused`, `test_an_order_whose_publish_failed_can_be_retried`). Like the stock levels, the memory is per process. Shipments in the gateway were already idempotent. The queue is at-least-once by design (ADR 0002), and the worker's shipment call is idempotent. |
| 3 | No race conditions | fixed | `Stock` and the gateway store are lock-guarded (`test_concurrent_reservations_never_oversell`). The new idempotency check holds a lock across check, reserve and publish; without it, the 16-retry test reserved more than once (mutant P6). The queue claims with a single `UPDATE ... RETURNING` (`4 threads claim 200 messages, each exactly once`). Go `-race` runs in CI (no cgo here). |
| 4 | Don't trust the clock | pass, with a stated limit | Span timings come from the OTel SDKs. The queue's `enqueued_at` and `claimed_at` are wall-clock epoch seconds because two processes (Python and Node) share them, and a monotonic clock does not cross processes. A clock jump changes only when a claim becomes visible again, never which message is delivered (FIFO by `id`, not by time). |
| 5 | Read before changing | pass | Every environment variable read (`INVENTORY_ADDR`, `QUEUE_TRACE_PROPAGATION`, `QUEUE_DB`, the gateway and worker variables) is listed in the README and validated at start (`test_main.py`, `message.test.ts`). |
| 6 | Never break compatibility | pass | Queue schema (`spec/queue.sql`, checked by both languages), message format and HTTP API are unchanged. The new 409 applies only to an `order_id` reused with different content. |
| 7 | One source of truth | pass | `spec/queue.sql` is the single schema; both queue implementations are tested to equal it. |
| 8 | Small changes, no secrets, validate input | pass | The secret grep found nothing. Orders, shipments, headers and bodies are size- and pattern-checked in all three languages. No new dependency. |
| 9 | Tests that can actually fail | fixed | No skips and no tautologies. Mutation check: 4 of 15 survived. One is equivalent; the other 3 now have tests. |
| 10 | Re-verify | pass | gofmt and `go vet` (with the e2e tag) clean; Go tests ok; ruff and mypy `--strict` clean; pytest 50 passed; tsc strict clean; `node --test` 47 passed; `make e2e`: `RESULT complete traces 21/21, distinct trace ids 21, spans per trace 11, languages per trace 3`, and the baseline test passed. govulncheck: `No vulnerabilities found.`; pip-audit: none; npm audit: 0. `audit_repo.py`: OK. |

## Known limitations

- The idempotency memory, like the stock levels, lives in the inventory process and is lost on
  restart. A production service would keep it in the same database transaction as the stock.
- Queue visibility timeouts use wall-clock time shared between processes (rule 4 above).
