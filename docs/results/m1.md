## End-to-end run (`make e2e`)

The test builds the gateway, starts the Python inventory, the Go gateway and the Node.js worker as
separate processes bound to 127.0.0.1 (ports chosen by the OS, read from each service's ready
line), points all three at an OTLP/HTTP receiver inside the test process
(`OTEL_EXPORTER_OTLP_ENDPOINT`, batch delay 100 ms), and kills the whole process tree of each
service at the end (`taskkill /T` on Windows, a process group on Linux). After both runs no
service process was left (checked with `Get-CimInstance Win32_Process`).

**`TestOneTraceSpansAllThreeLanguagesAndTheQueue`**: 20 concurrent orders, one order sent with the
caller's own `traceparent`, and one order for a sold-out SKU.

| Measure | Result |
|---|---|
| Orders whose trace has all 11 expected spans with the expected parents | 21/21 |
| Languages in each trace (`telemetry.sdk.language`) | 3 (go, python, nodejs) |
| Distinct trace ids for 21 orders | 21 |
| Spans carrying another order's `order.id` | 0 |
| Caller's trace id and parent span continued by the gateway | yes |
| Gateway state matches the trace (status `shipped`, tracking number equal to the `fulfillment.ship` attribute) | 21/21 |
| Sold-out order: business span in ERROR | only `inventory/inventory.reserve`; no PRODUCER or worker spans |
| Order accepted to shipment recorded (gateway server start to `order.mark_shipped` end), 21 orders | p50 492 ms, max 647 ms (second full check: p50 430 ms, max 573 ms) |
| Span end to arrival at the receiver | max 146 ms (second full check: 129 ms) |

**`TestBaselineWithoutQueuePropagationBreaksTheTrace`**: the same stack with
`QUEUE_TRACE_PROPAGATION=off`, so the producer writes no trace headers (the common bug).
5 orders: connected traces 0/5; every order became two traces, the front half (gateway and
inventory, 6 spans) and a separate back half rooted at the worker's CONSUMER span (5 spans). This
also shows the main test fails when propagation through the queue is broken.

## Quality control (DMAIC)

| Phase | This repository |
|---|---|
| Define | One order must be one trace across Go, Python and Node.js, including the hop through the queue, so an on-call engineer can see which service made it slow or fail. CTQs and targets are in [RFC 0001](../rfc/0001-design.md): 100 % complete traces and queue linkage, 0 leaked spans, failure attributed to the failing service, hostile headers harmless, spans exported in under 1 s, 0 known vulnerabilities. |
| Measure | Method: the e2e test reads every exported span back from an in-process OTLP receiver and checks service, kind, name, parent and language for all 11 spans of each order. Baseline (`QUEUE_TRACE_PROPAGATION=off`): 0/5 connected traces, 5/5 orphan consumer traces. With propagation: 21/21 complete, 21 distinct trace ids, 0 leaked spans, export lag max 146 ms. Unit tests: 157 passed. |
| Analyze | The baseline shows the defect this repo targets: without header injection the trace splits exactly at the queue, and the slow or failing back half is no longer findable from the request. The sold-out trace shows attribution works: the only ERROR business span is `inventory.reserve`, and the gateway's CLIENT span is marked ERROR for the 409 by the HTTP conventions while its SERVER span is not. The traces also exposed where time goes under 20 concurrent orders: `publish orders` took about 240 ms of a 345 ms request, because SQLite allows one writer at a time (ADR 0002); with sequential orders the same span took 18 to 28 ms. Defects found while building: the gateway's 409/404/502 responses carried no `order_id`, so a caller could not find the trace of a failed order (the e2e test timed out looking for it); the inventory's first body-limit middleware raised inside the app, which FastAPI turned into a 400 instead of a 413 for chunked bodies; `golang.org/x/net` v0.59.0 had GO-2026-6617 and pip 26.1.1 had two advisories. |
| Improve | The producer injects the context inside the PRODUCER span and the consumer extracts from `ROOT_CONTEXT`: 0/5 to 21/21 connected traces. Error responses now include `order_id`; the body limit buffers up to 4 KiB and answers 413 before the app runs; `x/net` was raised to v0.60.0 and pip to 26.2.1; govulncheck and pip-audit then reported nothing. The full check was run twice after the last change, both clean. |
| Control | CI (`ci.yml`) runs `make setup lint test` with the Go race detector, then `make e2e`, prints the e2e `RESULT` and `BASELINE` lines as `::notice` annotations (`::error` with the log tail on failure), then `make audit` (govulncheck, pip-audit, npm audit). Mistake-proofing in code: one `spec/queue.sql` checked by a test in Python and Node.js; strict typing (`mypy --strict`, `tsc --strict`), strict body schemas in all three services, bounded inputs (4 KiB requests, 16 headers of 1,024 characters, 64 KiB messages, 4 MiB OTLP bodies), exact dependency pins with Dependabot grouping the OpenTelemetry packages so API, SDK and instrumentation move together. |
